## BUG-13（P1，UI 重合）教程横幅与交互提示框画在同一位置，文字互相盖住

**实机证据**：把 Human 截图放大（`build/crop1.png`）可见「按 E 互动」（橙色，`tut.interact.body`）与「[E] 校园闲逛」（白色，`ui.prompt.hint`）**叠在同一行**，两个面板边框也彼此错位叠在一起。食堂室内截图同样复现。

**根因（数字对得上）**
- 提示框：`theme.py:78 RECTS["prompt"] = (130, 218, 220, 30)` → y 218..248，x 130..350；
- 教程横幅：`game/ui/tutorial.py:134 TutorialOverlay.BANNER_RECT = (120, 210, 240, 24)` → y 210..234，x 120..360；
- **两者在 y 218..234、x 130..350 完全重叠**，且都锚在画面底部中间、文字都带键位前缀 → 必然互相盖。

**修法**：把 `BANNER_RECT` 上移到 y≈180..204（提示框 218..248 之上；`RECTS["dialogue"]` 只在模态事件时占用，不同屏），**不做"互斥隐藏"**——横幅的唯一意义就是在玩家靠近可交互物时提示按 E，藏起来等于废掉教程。
**验收**：①`BANNER_RECT` 与 `RECTS["prompt"]` 矩形不相交；②**两者 label 的 y 不相交**（现在横幅 label 在 `tutorial.py:144` 的 `rect[1]+6`=**216**，提示框标题在 `prompt.py:39` 的 `rect[1]+2`=**220**，只差 4 逻辑像素 → 文字几乎同一条基线，这才是"重合"的主因）；③靠近可交互点且 `tut.interact` 激活时截图，两段文字不重叠。

## BUG-23（P1，**BUG-13 修复引出的回归**）横幅上移后压在对话框/头像/正文上，且开局第一屏必现

**修法（两行级，二选一）**
1. 把 `:293-294` 的 `refresh()` 挪到 `if locked` 之后（锁定态干脆不刷新）；
2. 或在 `locked` 分支补 `self.tutorial_overlay.hide()`（与 hud/prompt 同待遇）。
位置本身可以留在 y=180（与提示框不冲突），关键是**横幅不得与对话框共存**。

**验收**
1. 行为用例（已落地）：`tests/ui/test_tutorial_overlay_visibility.py::test_tutorial_overlay_hidden_while_overlay_open` —— 现在以 `xfail(strict=True)` 记录，**修好后会 XPASS 报红**，逼人删标记；反向用例 `..._visible_when_unlocked` 保证不会改成"一律隐藏";

## BUG-16（P1，穿模）2.5D 没有"按 y 排序"的遮挡规则，角色会被家具/道具盖住

**实机证据**：Human 截图 1 角色被长椅状道具压住一半；截图 2 角色半个身子嵌进家具方块。
**根因**
- 角色卡片 `render_pipeline.py:200 make_character_card()` 只设 `TransparencyAttrib.MBinary` / `setP` / `setLightOff`，**没有 `setBin`、没有 `setDepthOffset`**；
- 家具/道具 `interior_scene.py:61-63 make_box(..., 0.0, FURNITURE_HEIGHT, ...)` 是有高度的实体盒；
- 遮挡因此完全由 3D 深度决定，而不是"谁在玩家前面"——俯视 2.5D 里这就是必然穿模。
**修法**：角色与所有可遮挡物统一进固定 bin，按脚点 y 从远到近排 `sortOrder`（关闭彼此间深度测试）；或给角色卡 `setDepthOffset`。属渲染层，改前先离屏截图对比。
**验收**：站在家具正前/正后各一张截图，遮挡关系与脚点 y 一致。

## BUG-18（P2，露出画布外）室内没有相机取景/背景处理，房间小于视野就露黑底

**实测（读码 + 截图 2 对照）**
- `game/core/world_scene.py` `InteriorSceneAdapter._apply_scene_camera()` 与 `_update_scene_camera()` **两个方法体都是 `pass`**（校园侧有边界钳制，室内分支完全空）；
- 室内只靠 `on_enter` 里一次 `rig.set_interior(房间中心)` + `app.pipeline.align_camera(*rig.target)`；
- `render_pipeline.align_camera()`（`:168`）只按目标点摆相机，**没有任何缩放/取景参数**；
- 房间尺寸 16×10 米（5 个室内一致），而正交视野更宽 → 房间四周露出清屏色（截图 2 的大片深色边）。

**修法（三选一，按代价排序）**
1. 室内给相机加缩放（`align_camera` 增加可选 `zoom`/film size 参数），让 16×10 房间铺满 480×270；
2. 给室内画一圈"墙内底色"（比地面稍暗的矩形，覆盖视野），保证不露清屏色；
3. 最小改动：室内时把窗口 clear color 设为地面/墙面色（不是黑），至少不刺眼。
**验收**：5 个室内逐个截图，画面四周不出现清屏色；`InteriorSceneAdapter` 的两个相机方法不再是空实现（或明确写出为何不需要）。

## BUG-21（P1，玩家可见的内部键名）提示框把 `rel.npc_chenlang` 原样显示出来

**实测**（上表那些宽度就是用真实 preview 生成的，输出里能直接看到）：
```
join_club    '精力 -12  心情 -2  社交 +4  兴趣 +1  rel.npc_chenlang +3'
```
最后一项是**内部键名**，不是给人看的文案。

**根因（一行的事）**：`theme.py` 的 `_rel_sort_key()` 只认这些前缀：
```python
for prefix in ("rel_", "relationship:", "relationship_", "relationship."):
```
而内容里实际用的是 **`rel.npc_chenlang`（点号）** → 不匹配 → 返回 `("~", key)`；于是 `format_deltas()` 里
```python
elif _rel_sort_key(key)[0] == "":   # 永远为假
    stat_name = "关系"
else:
    stat_name = key                  # ← 原始键名漏到界面
```
"关系"这个兜底分支**对真实数据永远不触发**。

**影响范围**：9 个活动里 4 个会改关系（`join_club` / `play_games` / `create_work` / `library_study`）→ 玩家靠近这些交互点时，提示框第二行直接显示 `rel.npc_xxx +N`。
**修法（两处都做，缺一不可）**
1. **显示层（首选，最省）**：`prompt.py:68` 处把关系名喂进 `name_of`，`format_deltas` 先查 `name_of`，于是渲染成「与陈朗的关系 +3」：
   ```python
   for key in preview:
       short = theme._rel_sort_key(key)[1].removeprefix("npc_")
       name_of[key] = f"与{self.text_db.get_raw(f'npc.{short}.name')}的关系"
   ```
   （`npc.sumo.name` / `npc.chenlang.name` / `npc.xiaoyou.name` 文案齐全）
2. **排序层**：`_rel_sort_key()` 的前缀元组仍要补 `"rel."`——否则 `ordered_deltas()` 会把关系项当"未知键"排进 `"~"` 组，且 `stat_name = "关系"` 那条兜底永远不可达。只做 1 不做 2，显示对了但排序和兜底仍是坏的。
**验收**：4 个改关系的活动提示框不出现 `rel.` 字样；`ordered_deltas` 中关系项排在数值项之后；`_rel_sort_key("rel.npc_sumo")[0] == ""` 成立。

**修法（最小改动版，落在适配层，`flow.py` 一行不用动）**
`WorldSceneBase.on_enter`（`world_scene.py:171-172`）在写回 `location_id` 之前先判断：若 `spawn` 是室内 id（`map_data.has_interior(spawn)`，`map_data.py:424`），则取 `md.exit_point(spawn)` 得到 `(x, y, facing)`，把它当作 `position` 走 `:185-198` 那条既有分支（该分支会 `area_at(exit_x, exit_y)` 求室外区域并写回 x/y/facing）。这样"读档人在室内"和"从室内正常出门"走同一条路径。
⚠️ **注意**：只把存档里的**室内坐标**当 `position` 传下去**不管用** —— 实测 `area_at(208.0, 1.6) = None`，`:198` 会回落到旧 `location_id`（`loc_dorm`），仍然全废。必须传**门外落点**。
**同时堵掉复发口子**：`world_scene.py:198` 的 `area_at(...) or self._state.world.location_id` 就是本 bug 的真正成因——解析失败时把旧值（室内 id）原样留着，数据一改就无声复发；而 `:500`（InteriorSceneAdapter 出门）写的是 `or "loc_gate"`，**两处兜底不一致**。统一为「回落 `DEFAULT_SPAWN_LOCATION`（`flow.py:26`，别写裸字符串）+ `LOG.warning` 记一条」，让兜底是**响的**，不是静默的。

## 通用审视清单：**"这里的默认值出错时会骗谁？"**

同一个模式在本仓库已出现 5 处（每一处在失败时都给出**最误导的那个值**，而不是最安全的值）：
